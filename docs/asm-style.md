# Assembly annotation style

Rules for turning the generated byte-perfect disassembly (`engine/asm/swreg/src/swreg.asm`) into the
hand-maintained annotated source: the human-readable spec the C port is derived from
(`docs/porting.md` §2). The frozen generator output stays in `_ref/disasm/`.

## Invariant

Every edit is gated by `sh engine/asm/swreg/tools/verify.sh`: the build must print `SWREG.EXE: OK` and
`IDENTICAL` (per-instruction byte diff against `_ref/orig-bin/SWREG.EXE`). Annotations never
change instructions, data bytes, ordering or encodings; a batch that fails the gate is
reverted, not "fixed" by adjusting the reference.

Work is batched **per module** (one subsystem at a time) because one verification run costs
about a minute. Annotate what is about to be ported; do not sweep the file.

## Anatomy of the source

- 133 `S<frame>` segments, one routine each; `S0000` is the entry segment, `S1DEA` is DGROUP
  (`ASSUME DS:S1DEA`, so `[v_XXXX]` is DS:XXXX).
- Generated symbols:
  - `fn_XXXXX` — far-called / externally visible routine (also unreferenced entries),
  - `sub_XXXXX` — near-called local routine,
  - `loc_XXXXX` — intra-routine jump target (flow label),
  - `tbl_XXXXX` — table,
  - `v_XXXXX` — DGROUP variable at DS:XXXXX.
- Instruction syntax and hex formatting stay as generated (uppercase hex digits, `word ptr`,
  four-space indent). Do not re-wrap, reorder or reformat lines.

## Names

- Flow labels (`loc_`) are never renamed: they are jump plumbing, not meaning.
- `fn_`/`sub_`/`tbl_`/`v_` names get a semantic suffix in PascalCase, keeping the prefix:
  `fn_02385` -> `fn_EMSInit`, `v_0CA8` -> `v_EMSCachePages`. The `fn_`/`sub_` split (far vs
  near) is structural — keep it.
- Acronyms stay uppercase inside names: `EMS`, `DOS`, `VGA`, `OPL`, `BIOS`
  (`fn_DOSAlloc`, `v_EMSFrameSeg`).
- The original offset stays visible:
  - routine: the header line carries it — `; fn_EMSInit (0x02385) - ...`;
  - variable: its DGROUP definition label carries it (`v_EMSFrameSeg:  ; 0CAAh`),
    and the module banner lists the module's variables with offsets for
    orientation.
- A name is only given when the meaning is established for *all* uses. A DGROUP slot reused
  by unrelated code keeps its `v_XXXXX` name and gets a local comment instead of a misleading
  global name (example: `v_50D6`/`v_50D8` are the cache cursor in `fn_CacheInit` but a mode
  flag elsewhere).
- `EQU` for constants and struct field offsets once a layout is understood and used in
  several places. Single-use immediates stay numeric with a comment; do not convert a numeric
  operand to a symbol unless it is already written as one elsewhere (immediate encodings and
  relocations must stay identical). A layout shared by several segments lives in one block at
  the top of the file (before the first segment), e.g. `FILE_*` for the DOS file structs;
  module-local constants stay in the module banner.
- DGROUP structures and buffers that had no generated label get a `v_` anchor label with the
  offset kept in a trailing comment (`v_FileWorld:  ; 9093h`, `v_PalCurrent:  ; 4124h`).
  Anchors are orientation only: instructions keep their numeric immediates — writing
  `OFFSET v_FileWorld` would introduce a relocation.

## Comments

- **Module banner**: a `;` rule block above the segment that opens the module — purpose,
  platform requirements (EMS/DOS/BIOS), renamed variables with offsets, data layouts, seams.
- **Routine header**: every annotated routine, fixed shape:

      ; ---------------------------------------------------------------------------
      ; fn_EMSMapPages (0x0235B) - map a page list into the EMS frame.
      ; in:  DX = EMS handle, BX -> list: u16 count, then u16 logical, u16 physical
      ; out: -
      ; Notes: skips the call when this exact list is already mapped.
      ; ---------------------------------------------------------------------------

- **Inline comments** explain intent, invariants and data shapes, not the instruction (the
  instruction is already there): `add di, 6  ; one descriptor per slot`.
- Comments are plain ASCII, one thought per line, no enforced comment column (small diffs
  beat alignment).
- Unknowns are marked as such (`; not yet identified`) instead of guessed.

## Seam tags

Platform access is tagged where it happens — on the `int`/port instruction itself:

    int 67h                 ; SEAM EMS: 50h/00h - map multiple pages

- `grep '; SEAM'` is the boundary inventory: every direct `int`/port access in annotated code
  must carry a tag. That set is exactly what the platform layer replaces.
- Families: `VIDEO`, `AUDIO`, `INPUT`, `TICK`, `CONTROL` — the companion protocol's message
  families (`docs/protocol.md`) — and the engine-internal platform services `EMS`, `DOS`,
  `BIOS`, `MOUSE`, `SOUND`.
- A wrapper routine carries the tag inside itself (`fn_DOSAlloc` around int 21h 48h); callers
  only name the wrapper.
- Stream rules (`docs/porting.md` §5): only VIDEO (mode/palette/dirty rects), AUDIO (OPL
  register writes), INPUT, TICK and CONTROL ever cross to the client; EMS, DOS and BIOS never
  do. The tag names the operation the client or platform layer must provide, e.g.
  `; SEAM VIDEO: palette 0..255`, `; SEAM AUDIO: OPL write port 388h`.

## Workflow

1. Pick the module; read its routines and collaborators, confirm variable roles across all
   their uses.
2. Rename symbols (exact, whole file), then add banner, headers, tags and inline notes.
3. Run `sh engine/asm/swreg/tools/verify.sh`; require `SWREG.EXE: OK` + `IDENTICAL`.
4. Commit as `disasm: annotate <module>`; list open questions in the commit or the module
   banner rather than inventing meaning.

## What not to do

- No semantics, no restructuring, no macro-ization beyond the proven `x_cmp_*` macros.
- No renaming across unrelated modules for taste; annotate just-in-time.
- No edits under `_ref/` (read-only, hook-enforced).
